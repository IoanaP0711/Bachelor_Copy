Interface guide

Help & Glossary

This guide explains the terms, indicators, charts, and actions used by the intrusion detection system. It is intended for both technical users and people with limited networking experience.

An unusual connection is not automatically an attack. The system combines the model result with contextual information, repetition, and analyst review.

Section 1

System overview

Back to top

Complete processing flow

Network traffic→ Traffic features→ Autoencoder→ Anomaly score→ Raw severity→ Contextual filtering→ Repeat-based analysis→ Final decision→ Explanation→ Analyst review
  1. The application observes network communication records.
  2. Relevant numeric characteristics are extracted from each communication.
  3. The autoencoder compares those characteristics with behavior learned as normal during training.
  4. The reconstruction difference becomes the anomaly score.
  5. Configured thresholds convert that score into an initial raw severity.
  6. Contextual rules and recent repetition are considered without deleting the original raw result.
  7. The system produces a final decision and an explanation for the operator.
  8. A human analyst may update the investigation status or record feedback.

Decision support, not automatic proof

The interface helps a person prioritize and understand unusual traffic. It does not replace human judgment, confirm an attack by itself, or explain every possible cause of a network event.

Section 2

Final decisions

Back to top

OK

The system did not identify behavior that currently requires attention.

BENIGN

The traffic may look unusual to the model, but the available context suggests that it is probably legitimate.

REVIEW

The behavior should be checked by a person. It may be harmless, but the available information is not sufficient to dismiss it automatically.

CRITICAL

The behavior appears strongly suspicious or repeatedly abnormal and should be investigated promptly.

Important: REVIEW does not mean a confirmed attack. CRITICAL also does not prove an attack by itself. These labels are assessments produced by the detection system.

Section 3

Raw severity versus final decision

Back to top

Why two labels are shown

Raw severity is the autoencoder pipeline's initial classification based on the anomaly score and thresholds. Final decision is the operator-facing assessment after contextual filtering and repeat-based analysis. The values may stay the same, decrease, or increase.

The Changed by context badge means the final displayed assessment differs from the raw model label. It does not mean the original result was erased.

Raw OK

The anomaly score is below the configured OK boundary.

Raw WARN

The score is above the OK boundary but below the configured warning boundary.

Raw MED

The score is above the warning boundary but below the critical boundary.

Raw CRIT

The score is at or above the configured critical boundary.

CRIT → REVIEW

The model found a large deviation, but the available context reduced the operator-facing result to something requiring review rather than immediate critical treatment.

WARN → BENIGN

The model marked the record as unusual, while contextual information identified a likely legitimate communication type.

MED → OK

The raw model score crossed an anomaly band, but the current contextual rules determined that no attention was needed.

Context does not always lower severity. Repeated unknown or uncommon traffic can preserve or escalate the result under the current repeat logic.

Section 4

Anomaly score

Back to top

What the score means

The autoencoder attempts to reconstruct the traffic features it receives. The reconstruction error measures the difference between the original feature values and the reconstructed values. That error is used as the anomaly score.

A larger score usually means the record differs more from the behavior learned by this model. It is not automatic proof of malicious activity and it is not a universal percentage or attack probability.

Section 5

Contextual filtering

Back to top

Definition

Contextual filtering uses additional information about the communication to interpret the initial model result.

Context can include local or external communication, known traffic classes, protocol and port information, repeated behavior, Suricata information when available, and previously observed activity.

Contextual filtering does not erase the raw result. Raw severity remains visible separately from the final decision.

Section 6

Repeat-based analysis

Back to top

Why repetition matters

One unusual event may be accidental. Repeated similar events may deserve more attention. Repetition is additional evidence, not proof of an attack.

Exact repeat pattern

The repeat key uses normalized values for source IP, destination IP, protocol, traffic class, and destination port. Two records belong to the same exact pattern only when these normalized values match.

  • Source IP
  • Destination IP
  • Destination port
  • Protocol
  • Traffic class

For current DNS and local-discovery traffic, the backend normalizes destination port to 0 for repeat matching.

Section 7

Temporal context

Back to top

First seen

The earliest available time when the matching communication appeared in the history used for the calculation.

Last seen

The most recent available time when the matching communication appeared.

Flows from the same source

Counts all available records from the same source IP, even when the destination, port, protocol, or traffic class differs.

Exact-pattern occurrences

Counts records matching the same source IP, destination IP, destination port, and protocol in the temporal-context calculation.

Repeat count

The count attached by the short-window repeat logic when that value is available. It may differ from a broader historical count.

Last 24 hours

When timestamped history exists, the temporal calculation uses the most recent available 24-hour period.

Current buffer

Only records currently held by the running application were used. This does not necessarily represent the complete network history.

Section 8

Repeated Pattern View

Back to top

How records are grouped

The Patterns page groups anomaly-related communications sharing the same source IP, destination IP, destination port, protocol, and traffic class.

Count

The number of records in the grouped pattern.

First seen

The earliest timestamp available for that grouped pattern.

Last seen

The latest timestamp available for that grouped pattern.

Current pattern fields

The uploaded backend currently exposes highest raw severity, highest final decision, and a short reason for each repeated pattern.

A high repeat count does not automatically indicate malicious activity. Common legitimate services may also communicate frequently.

Average anomaly score, maximum anomaly score, and per-decision counts are not fields in the current uploaded /patterns response. They should only be documented as visible fields after the backend actually exposes them.

Section 9

Basic networking terms

Back to top

IP address

An address that identifies a device or network endpoint for communication.

Source IP

The address from which the observed communication originated.

Destination IP

The address receiving the observed communication.

Source port

Usually the temporary application-side communication endpoint used by the source.

Destination port

Often indicates the service the source is trying to reach.

Address and door analogy

An IP address is similar to a building address, while a port is similar to a numbered door used by a particular service. This is only an analogy; real network behavior is more flexible.

Packet

A small unit of data transmitted through a network.

Flow

A set of related packets or a summarized communication between endpoints.

Protocol

A set of rules that determines how systems communicate.

Local address

An address treated as part of the monitored internal or private network.

External address

An address outside the local monitored network. External does not automatically mean hostile.

Traffic class

A readable category assigned to a type of communication, such as DNS or local discovery.

Throughput

The amount or rate of traffic records processed over time. The dashboard currently shows rolling backend requests per second.

Section 10

Protocols

Back to top

TCP — Transmission Control Protocol

Establishes a connection and coordinates ordered, confirmed delivery of data.

UDP — User Datagram Protocol

Sends data with less delivery coordination and is commonly used when speed or low overhead matters.

ICMP — Internet Control Message Protocol

Carries network control and diagnostic messages, including communication associated with ping.

HTTP — Hypertext Transfer Protocol

A protocol commonly used for unencrypted web communication.

HTTPS — Hypertext Transfer Protocol Secure

Web communication protected with encryption, normally using TLS.

DNS — Domain Name System

Converts human-readable names, such as website names, into IP addresses and provides related naming information.

A protocol is not automatically safe or malicious. Its meaning depends on who communicated, where, how often, and what surrounding behavior occurred.

Section 12

Feature contributor chart

Back to top

How to read the chart

  • Each bar represents one input feature used by the model.
  • Longer bars represent larger stored reconstruction differences or contributor values.
  • Feature names identify the measured traffic characteristics.
  • The values are not necessarily percentages.
  • Contributors explain model deviation, not attack causality.
Feature contributors show which values influenced the anomaly score most strongly. They do not independently prove why the traffic occurred or whether it was malicious.

Section 14

Human alert status

Back to top

Human status describes investigation progress. It is separate from the model's raw severity and the system's final decision.

New

No analyst progress has been recorded yet.

Seen

An analyst has acknowledged or viewed the alert.

Under review

The alert is currently being investigated.

Resolved

The analyst considers the investigation complete.

False positive

The analyst recorded that the alert did not represent a relevant threat.

Example

A CRITICAL alert may have the human status Under review. CRITICAL is the system assessment, while Under review describes the analyst's progress.

Setting False positive does not modify the historical raw severity or final decision.

Section 15

False-positive marking

Back to top

What the action does

  • Records analyst feedback for the selected alert.
  • Does not automatically retrain the model.
  • Does not automatically change thresholds.
  • Does not automatically whitelist the communication.
  • Does not remove or overwrite the original final decision.

The original result is preserved so later reviewers can see what the system produced at detection time and what the analyst concluded afterward. This supports auditability.

Section 16

JSON report export

Back to top

JSON — JavaScript Object Notation

A structured, machine-readable text format. It may not look like a formatted human report, but software tools can parse it reliably.

Current exported fields

The current uploaded backend exports the alert timestamp and identifier, network endpoints and ports, protocol, traffic class, raw severity, final decision, anomaly score, contextual reason, repeat count and window, top contributors, explanation levels, and recommended action.

Human status, false-positive feedback, the complete temporal-context object, and replay metadata are not currently added to the uploaded JSON-report builder. Do not promise those fields unless the report implementation is extended.

Section 17

Replay / Demo Mode

Back to top

How replay works in the current backend

Replay uses previously saved event records for controlled demonstration and validation. The stored processed examples are inserted into the interface again. This does not mean that live traffic was captured or that the model was executed again.

Saved final decisions are preserved. Replay does not rerun model inference, contextual filtering, or repeat-based decision logic for those stored records.

Current operating mode

Loading current mode…

The current uploaded backend does not provide a separate Clear demo records endpoint. Its existing Clear alerts action clears the alert buffer, recent-traffic buffer, and repeat memory. It must not be described as demo-only unless a separate implementation is added.

The shared CSS currently defines an amber REPLAY MODE badge. A separate record-level DEMO badge style was not present in the uploaded shared stylesheet.

Section 18

Metrics and system state

Back to top

CPU usage

The percentage of processor capacity used by the monitoring process when measured.

Memory usage

RSS memory is the amount of physical memory currently used by the process, usually shown in megabytes.

Throughput

The rolling processing rate, currently represented as backend requests per second.

Buffered alerts

Anomaly-related alert records currently held in the application's in-memory buffer.

Request count

The total number of prediction requests recorded by the metrics system, when that measurement is shown.

System health

A summary of whether the application and its monitored components are responding as expected.

Last updated

The most recent time the displayed interface data was refreshed.

Configuration source

Indicates whether validated runtime values came from the configuration file or from safe defaults.

High CPU or memory values describe the monitoring application's resource state. They do not directly indicate a cyberattack.

Section 19

Suricata

Back to top

Role in the system

Suricata is a network threat-detection engine. It can produce signature-based alerts and network metadata that may enrich the AI-based system.

A Suricata alert and an autoencoder anomaly result are not the same thing. Not every observed flow has a matching Suricata signature alert.

Section 21

Interface actions

Back to top

Quick view

Opens a compact alert preview without leaving the current page.

Details

Opens the full alert-detail page.

View matching alerts

Shows alerts associated with a selected communication pattern when the Patterns interface provides that action.

Open latest alert

Opens the most recent alert associated with the selected item when available.

Change status

Updates the human investigation status without changing the system's historical model result.

Mark as false positive

Records analyst feedback while preserving the original alert.

Export JSON report

Downloads the current machine-readable report for an alert.

Start replay

Starts inserting saved processed events into the normal interface buffers when the application is configured in replay mode.

Stop replay

Stops future replay insertions. It does not automatically remove records already inserted.

Clear alerts

The current backend clears alerts, recent traffic, and repeat memory. It is not a demo-only clear action.

Filter

Changes which records are displayed. It does not modify stored alerts.

Search

Finds matching displayed records or help topics without changing stored data.

Logout

Ends the current dashboard session and returns to the login page.
